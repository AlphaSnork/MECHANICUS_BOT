## Партия №7: исправление ошибок хостинга (2026-10-04)

Логи с bot-hosting.net:
1. `AttributeError: 'ShopView' object has no attribute 'message'`
2. `403 Forbidden (code 50013): Missing Permissions` при уведомлении администратума.

Причины и фиксы (все в bot.py, единственном файле кода):
1. МОЙ БАГ: у `discord.ui.View` нет атрибута/свойства `message` ни в одной версии discord.py
   (проверено на 2.3.2 и 2.7.1: hasattr(View,'message')==False; `message` есть у Interaction, не у View).
   Использование self.message падало при нажатии «Купить» и при таймауте меню.
   Фикс: собственная ссылка `host_msg`, запоминаемая через `interaction.original_response()`
   (MenuMixin.bind / HelpView.bind); все обращения переведены на неё; `self.message` в коде = 0.
2. Уведомление администратума сначала делало роль mentionable (`role.edit`); если роль бота НИЖЕ
   роли уведомлений в иерархии (или нет Manage Roles), edit возвращал 403 и ронял ВСЮ отправку.
   Фикс: переключение mentionable — best-effort в отдельном try/except с подсказкой в лог;
   отправка выполняется всегда; в allowed_mentions передаётся явный id роли;
   при ошибке отправки — понятное предупреждение (права в канале / иерархия).
   Примечание: право «Администратор» НЕ отменяет иерархию ролей — бот не может редактировать
   роли выше своей верхней, поэтому 403 на role.edit возможен даже с админом.

Проверки: харнес 51/51, включая два новых регресс-теста, воспроизводящих оба логовых сценария
(уведомление уходит при 403 на role.edit; кнопка покупки обновляет витрину без AttributeError).
--selftest ОК; data/ нетронута.

## Партия №8: фикс «Приложение не ответило вовремя» (2026-10-04)

Скриншот пользователя: нажатие «Использовать предмет» в /lv inventory → ошибка Discord
«Приложение Lex Veritas [Role Play] не ответило вовремя».
Причина: в колбэке `_on_use` уведомление администратума (2–3 последовательных HTTP-запроса:

отводит на ack ~3 секунды; при любой задержке взаимодействие протухало.
Фикс: `interaction.response.edit_message(...)` (ack) перенесён первой строкой, уведомление
и followup-сообщения идут после. Остальные колбэки проверены: ack везде стоит до сетевых вызовов
(perform_purchase отвечает первой строкой; loot/moderation/giveaway/tarot до ack делают только
локальные операции и файловый ввод-вывод).
Регресс-тест в харнесе: порядок вызовов ['ack', 'notify', 'followup'] — 52/52 ОК.

## Партия №16: крах «Session is closed» — единственный bot.run + проба интентов (2026-10-04)

Лог хостинга: PrivilegedIntentsRequired (Presence не включён в портале) → фолбэк пытался
второй bot.run() на том же экземпляре → RuntimeError: Session is closed (discord.py закрывает
HTTP-сессию после первой попытки; Client не перезапускаем) → демон отключил авторестарт.
Фикс архитектуры запуска:
- bot.run(token) вызывается РОВНО ОДИН раз;
- перед запуском — проба гейтвея `_gateway_probe()` (GET /gateway/bot + ws identify с целевыми
  интентами): 'ok' | 'privileged' (close 4013/4014 или op 9) | 'auth' (401/4004) | 'error';
  по результату отключаются только неразрешённые интенты (сначала presences, затем members);
- ручные переопределения: Env INTENTS_PRESENCES=0 / INTENTS_MEMBERS=0;
- если проба недоступна (сеть) — старт с настроенными интентами; последний страховочный
  except PrivilegedIntentsRequired теперь логирует подсказку и завершается без повторного run.
Тесты: +4 (единственный bot.run, проба async, fake-token → auth, env-флаги). Харнес 97/97 ОК.

Лог после партии №16: проба не спасла — PrivilegedIntentsRequired всё равно прилетел на bot.run,
страховочный except вышел с кодом 1. Анализ: проба давала ложный результат (тихий 'error' или
несработка close-кода), а её лишняя identify-сессия к гейтвею накладывалась на запуск
(«session has been invalidated» ×2 в логе) — класс ошибок, который нельзя считать приемлемым.
Решение: автопроба УДАЛЕНА полностью; схема детерминированная:
- intents.members = 1 по умолчанию (приветствия; портал пользователя Members Intent разрешает);
- intents.presences = 0 по умолчанию (онлайн — opt-in: Presence в портале + INTENTS_PRESENCES=1);
- Env-флаги INTENTS_MEMBERS / INTENTS_PRESENCES — ручное управление;
- bot.run() однократно; при старте лог печатает активные интенты;
- страховочный except PrivilegedIntentsRequired логирует подсказку про Env-флаги (без повторного run).
Тесты: проба-проверки заменены на проверки дефолтов (members=True, presences=False, отсутствие
_gateway_probe). Харнес 97/97 ОК; selftest ОК; data/ чистая.
Действие пользователя: залить bot.py и нажать Start вручную (авторестарт инстанса был отключён
демоном после краха); Env для базовой работы не нужны.

## Партия №24: фикс маппинга публикаций форума (r6) (2026-10-10)

Причина: у discord.py WebhookMessage НЕТ атрибута channel_id; id созданной через thread_name

каждое следующее сообщение снова шло путём thread_name.
Фикс: tid = sent.channel_id or sent.channel.id (+ страховка tid != target.id); маппинг пишется
в thread_map и сохраняется. Маркер сборки: 2026-10-10.r6-thread-map-fix.
Тесты 8p: первое сообщение создаёт пост (thread_name), маппинг =991, второе идёт thread=991.
Харнес 133/133 ОК. Контроль файла: 4300 строк, md5 8dbbbd373a8acf941b38c60901af2e26.
Восстановление после дублей: вручную удалить посты-дубли в целевом форуме, удалить старые
задачи переноса (🗑) и создать заново (у старых history_done=True и битый thread_map).
